# Методика показателей

Документ — договорённость между конвейером (`pipeline/`) и независимой проверкой (`verifier/`).
Проверка не читает код конвейера: она считает всё заново по этим правилам и сверяет с выпуском.

## Исходники

| Файл | Что |
|---|---|
| `data/journal.csv` | проводки: дата, Дт, Кт, сумма в рублях с копейками, статья затрат |
| `data/accounts.csv` | план счетов; `type = pl` — счета финансового результата (20, 26, 44, 90.*, 91.*, 99) |
| `data/mapping.csv` | правило разноски ноги проводки по статье управленческого P&L: счёт + сторона (D/C) + статья затрат → статья; `тех` — закрытие счетов |
| `data/commentary.csv` | причины отклонений — пишет экономист |
| `data/reissue/reissue_reasons.csv` | только у перевыпуска: причины изменений к отправленному выпуску — `article`, `month`, `owner`, `cause`; пишет владелец статьи, чисел в тексте нет |

Выпуск 2 (перевыпуск за тот же отчётный месяц) лежит в `data/reissue/`: тот же набор файлов плюс причины.

**Канонический хэш** исходника: таблица читается целиком как текст, колонки сортируются по имени,
пишется CSV с переводом строки LF без индекса, от UTF-8 байтов берётся SHA-256 (BOM исходника в канон не входит). Хэш выпуска —
в `output/manifest.json`. Исходники и реестр хранятся в UTF-8 с BOM, чтобы Excel открывал их без мастера импорта.

## Знак

Каждая проводка даёт две ноги: дебетовую со знаком минус и кредитовую со знаком плюс.
Доходы положительны, расходы отрицательны.

## Управленческий P&L

Статья месяца — сумма ног по счетам `pl`, которым маппинг назначил эту статью (ноги `тех` не входят).
Промежуточный итог — сумма всех статей выше него.

| № | Строка | Вид |
|---|---|---|
| 1 | Выручка | статья |
| 2 | Материалы | статья |
| 3 | Персонал производства | статья |
| 4 | Энергия | статья |
| 5 | Ремонты | статья |
| 6 | Прочие производственные | статья |
| 7 | Валовая прибыль | итог |
| 8 | Коммерческие расходы | статья |
| 9 | Управленческие расходы | статья |
| 10 | EBITDA | итог |
| 11 | Амортизация | статья |
| 12 | Прибыль от продаж | итог |
| 13 | Проценты | статья |
| 14 | Прочие доходы и расходы | статья |
| 15 | Прибыль до налога | итог |
| 16 | Налог на прибыль | статья |
| 17 | Чистая прибыль | итог |

**Контроль с бухгалтерией:** чистая прибыль месяца = сумма всех ног по счёту 99 за месяц.

## Периоды

Отчётный месяц — последний месяц в проводках. Сравнение — с тем же месяцем прошлого года.
Нарастающий итог `NМГГГГ` — месяцы с января по отчётный; база — те же месяцы прошлого года.

## Меры реестра (`output/registry.csv`)

| Мера | Формула | Единица |
|---|---|---|
| значение | сумма строки за месяц или нарастающий итог | ₽, 2 знака |
| изменение | факт − база | ₽, 2 знака |
| изменение % | (факт − база) / \|база\| × 100; нет числа при нулевой базе | %, 1 знак |
| рентабельность % | строка / выручка × 100 (валовая прибыль, EBITDA, прибыль от продаж, чистая прибыль) | %, 1 знак |
| отклонение сверх роста выручки | факт − база × (выручка факта / выручка базы), для статей 2–6, 8, 9, 11, 13, 14 | ₽, 2 знака |

Изменение % считается к модулю базы, поэтому минус всегда значит «хуже для прибыли»: расходы выросли
или доход упал. Отклонение сверх роста выручки отрицательно, когда статья расходов выросла быстрее
выручки. Для постоянных и финансовых статей (амортизация, проценты, разовые прочие) сравнение
с пропорцией выручки условно: оно показывает, сколько статья «съела» сверх нормального масштаба.

Реестры сверяются между собой по ключу (показатель, мера, период), не по `id`.

Слепая проверка сравнивает реестр со своим пересчётом так: ₽ — точно, в копейках (в реестре не больше
двух знаков, и это пересчёт, округлённый до копейки; дробным бывает только отклонение сверх роста выручки),
в том числе строки «было при отправке» и «изменение к отправке»; % — с допуском в половину последнего
знака реестра (0,05).

**Где число стоит** (`shown_in`) — по факту готовых файлов выпуска, через «, »: `html` — выведено числом
в отчёте (`data-r`), `chart` — по строке построен график отчёта (атрибут `data-rows`, чисел на графике нет),
`xlsx` — число есть в книге Excel (лист «P&L» или «Изменения»), `registry` — только в реестре (справочные
строки и кандидаты в отклонения ниже порога).

## Перевыпуск

Отчёт за месяц уже отправлен (выпуск 1), потом в учёт попали правки — выпуск 2 за **тот же** отчётный
месяц. Выпуск 2 сверяется с реестром отправленного выпуска по ключу (показатель, мера, период).

- **Изменение** — точное сравнение: ₽ — в копейках, % — в единицах последнего знака реестра (0,1 п. п.,
  как в отчёте). Строки «было при отправке» и «изменение к отправке» в сравнение не входят.
- **Первичное изменение** — статья P&L (строки 1–6, 8, 9, 11, 13, 14, 16) за месяц, мера «значение».
  Только у него бывает причина: строка `reissue_reasons.csv` с той же статьёй и месяцем.
- **Производное изменение** — всё остальное (итоги, нарастающий итог, изменение, %, рентабельность,
  отклонение). Оно объяснено, если изменилась хотя бы одна статья за месяц, из которых оно складывается:
  статья — сама, итог — статьи выше него, рентабельность и отклонение — ещё и выручка; месяцы — месяцы
  периода (нарастающий итог — с января, сравнение «A к B» — оба периода).
- **Выпуск останавливается**, если статья за месяц изменилась без причины; причина есть, а статья за месяц
  не изменилась; производное число изменилось без изменения своих статей; строка есть только в одном из
  выпусков; отчётные месяцы разные; в причине есть цифры; в данных есть причины, а отправленный выпуск
  не указан.

Каждое изменившееся **значение** (любая строка P&L, месяц или нарастающий итог) получает в реестре
выпуска 2 две строки:

| Мера | Формула | Источник (`source`) |
|---|---|---|
| было при отправке | значение того же ключа в реестре отправленного выпуска | `registry.csv отправленного выпуска, SHA-256 …` |
| изменение к отправке | стало − было, где стало — строка «значение» выпуска 2 | расчёт из значений реестра |

Канонический SHA-256 отправленного реестра записан в `manifest.json` (`previous_registry`). Блок отчёта
«Что изменилось с прошлой отправки» и лист книги «Изменения» выводят для каждого такого значения было,
стало, изменение и причину (у статьи за месяц — текст владельца, у итога — статьи, из-за которых он
изменился). Изменившиеся Δ, % и рентабельность в блок не выводятся: они следуют из тех же статей и
проверяются контролем.

**Слепая проверка перевыпуска** (`--previous`, по желанию `--previous-data`): проверяющий сам находит
изменившиеся значения, сравнивая свой пересчёт выпуска 2 с отправленным реестром; «было» сверяет с
отправленным реестром — это документ, который ушёл руководителю, — а его SHA-256 с манифестом выпуска 2;
с `--previous-data` ещё и пересчитывает отправленный реестр из исходников выпуска 1. «Стало» и изменение —
свой пересчёт. Статья за месяц изменилась без причины или причина без изменения, изменение не показано
в блоке или в блоке нет причины — расхождение.

## Отображение в отчёте

Суммы — в млн ₽ с одним знаком, проценты — с одним знаком; округление половина вверх. Пробел —
разделитель тысяч, запятая — десятичный знак, «−» — минус. Каждое число HTML выводится как
`<span data-r="<id>" data-f="<формат>">`; формат — `mln` или `pct` с флагами через `|`:
`+` — плюс у положительных, `abs` — модуль, `neg` — сменить знак (флаги применяются в порядке neg, abs).
Число в видимом тексте вне такой разметки — ошибка. Числами не считаются: даты и месяцы (`ГГГГ-ММ`,
`ГГГГ-ММ-ДД`), метки нарастающего итога (`9М2026`), годы, шестнадцатеричные хэши и слово «SHA-256».

**Форматы**, допустимые для чисел отчёта (статьи расходов — строки 2–6, 8, 9, 11, 13, 14):

| Мера | Формат |
|---|---|
| значение | `mln`; у статей расходов также `mln\|abs` |
| изменение | `mln\|+` |
| изменение % | `pct\|+`; у статей расходов также `pct\|neg\|+` (рост расходов — с плюсом); у выручки `pct\|abs` |
| рентабельность % | `pct` |
| отклонение сверх роста выручки | `mln\|abs` (знак передаёт слово «хуже» / «лучше») |
| было при отправке | `mln` |
| изменение к отправке | `mln\|+` |

Проверка сверяет число с пересчётом по его ключу (показатель, мера, период) и формат — с этой
таблицей. Подходит ли ключ месту в отчёте (колонке, фразе), автоматическая проверка не решает —
это пункт чек-листа приёмки.
