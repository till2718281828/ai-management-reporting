# Выпуск отчёта руководителю

Читатель отчёта — руководитель без времени и без операционного опыта. После чтения у него должно
остаться ощущение, что он понимает, что происходит внизу. Отчёт отправляется только после того, как
его числа сошлись трижды: в контролях конвейера, в слепой проверке и в чек-листе приёмки.

## Порядок

1. **Вопросы до работы** — спросить одним раундом, с рекомендацией к каждому:
   - отчётный период и база сравнения (по умолчанию — тот же период прошлого года);
   - менялись ли исходники или правила разноски с прошлого выпуска;
   - есть ли у экономиста причины отклонений (`data/commentary.csv`) — без них отчёт выйдет
     с пометкой «причина не установлена».
2. **Прогон:** `python -m pipeline.run`. Код 1 — читать `output/controls.md`, разбирать ошибку
   по исходникам; не править готовый отчёт руками и не ослаблять контроль.
3. **Автоматическая слепая проверка:** `python -m verifier.recompute`. Расхождения — стоп.
4. **Слепая проверка агентом:** вызвать субагента `blind-verifier`. Он не видит кода конвейера и
   считает сам. Его протокол показать пользователю как есть.
5. **Приёмка** по [checklist.md](checklist.md): каждый пункт — «да» или согласованное отступление.
   Пункты, которые требуют суждения (подходит ли число месту, понятна ли фраза), решает человек.
6. **Отправка** — только после явного «ок» пользователя. Число в тексте письма — только из реестра.

## Правила

- Число попадает в отчёт только из реестра (`output/registry.csv`), а в реестр — только из расчёта
  по исходникам. Ручная правка числа в отчёте — ошибка выпуска, даже если число «правильное».
- Факт и гипотеза разделены: причина отклонения — только от владельца статьи (`commentary.csv`).
  Нет причины — так и пишется.
- Методика расчёта — `docs/methodology.md`. Меняется методика — сначала документ, потом код
  конвейера и проверки.
